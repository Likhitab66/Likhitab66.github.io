The problem

When a live stream breaks mid-game, someone has to find out why, fast. Live sports traffic swings on purpose: a kickoff spike or a halftime dip looks like an incident to a naive detector, and a real fault can hide inside that noise. I built an agent that investigates incidents on a fully synthetic live-sports streaming day for a fictional league. Every fault is injected with a hidden label, so its accuracy is measured instead of guessed.

How it works

  1. Simulate

    A seeded simulator generates a synthetic broadcast day with injected faults, hidden ground truth, and deliberate data warts like duplicate events and clock skew.

  2. Detect

    Event-aware baselines expect the kickoff surge and the halftime dip, so only real anomalies become incident tickets.

  3. Investigate

    A bounded planning loop calls 8 typed tools over a governed, read-only DuckDB semantic layer, tests hypotheses, and widens scope when the evidence is thin. The agent has no raw SQL path.

  4. Guard

    The agent runs behind four guardrails, which check the ticket, every tool call, every tool response, and every number in the memo against the trace step it cites.

  5. Read out

    The A/B module runs a chi-square sample-ratio-mismatch gate first and refuses to estimate effects if it fails, then reports effects with the MDE at 80% power.

  6. Evaluate

    A battery of 33 scenarios scores root-cause accuracy against the hidden labels: 25 core fault scenarios, 5 clean synthetic worlds, 2 held-out scenarios and 1 deliberately ambiguous incident.

How I measured it

  • On the 25 core fault scenarios: detection 25/25, precision@1 1.00 and recall@1 1.00
  • Memo grounding 1.00: every figure in every incident memo matched evidence from the trace step it cites
  • 0 false alarms on 5 clean synthetic worlds
  • Mean time to detect 11.9 min on the core battery. One capacity scenario detects before its labeled onset and counts as a negative value; without it the mean is about 13.3 min.
  • Held-out recall@1 0.50, and the ambiguous case is wrong at top-1 and right at top-3, kept in the battery on purpose
  • Doctored memo numbers that get past the number guard: 0.1%, down from 30.2% under a naive whole-trace match

Limits

  • All data is synthetic, from a seeded simulator and a fictional league. Nothing comes from a real streaming service.
  • Every measured number comes from the deterministic planner. The optional local LLM planner is unit-tested but not part of the measurements.
  • The deterministic planner is a codified on-call playbook, and the core battery draws on the same six fault types, so the core 1.00 is in-distribution. The held-out pair, with parameters outside every tuned range, is the harder test: it found the cause for one of the two.
  • One held-out scenario sat below the detector's sensitivity floor and was not detected at all. I left it in the report.

What I'd tell the team

  • Trust the agent's first pick on the fault types its playbook covers, and treat anything new as a lead for a person to check: on held-out faults its recall@1 fell to 0.50.
  • The A/B readout is the piece I would put in front of a team first. It refuses to estimate when the split fails its sample-ratio check, and when conversion rose but p90 time to first frame got worse, it reported both and recommended no-ship.
